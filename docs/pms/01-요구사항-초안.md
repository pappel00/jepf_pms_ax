## 1. 원본 WBS 문서 구조 분석

엑셀 파일은 시트 8개로 구성되어 있고, 각 시트가 실제로 PM이 관리하던 정보 단위를 보여준다.

| 시트 | 성격 | 핵심 내용 |
|---|---|---|
| 표지 | 문서 메타 | 사업명, 문서명, 파일명, 작성일자 |
| 개정이력 | 버전관리 | No/버전/변경일/변경사유/변경내용/작성자/승인자 — 문서 자체의 이력 |
| 마일스톤 | 사업 전체 일정 | 사업 전체기간, 단계별(착수→분석→설계→구현→통합테스트→시범오픈→그랜드오픈→안정화) 시작일/종료일. **요구사항이 1차(RFP/개선요구사항)→2차(갭분석 REVIEW)→3차(TFT 요구사항)로 차수를 거쳐 정련되는 과정**이 별도 항목으로 명시돼 있음 |
| WBS / WBS (2) | 실행 계획+실적 | 아래 2절 참고 (WBS(2)는 이전 스냅샷으로 보임 — 기준일자만 다르고 구조 동일) |
| 인력투입계획 | 자원 계획 | 파트(총괄/그룹웨어/협업/ECM 등)-역할(PM/PMO/PL/개발/QA/디자인 등)-담당자-등급(특급/고급/중급/초급)-상주여부, 월별(M~M+6) 계획 공수(MM) vs 실적, 파트별 소계/전체 합계 |
| 제품 버전 | 사업 기준정보 | 프로젝트명/기간/오픈일 등 사업 개요, 제품(플랫폼) 버전 선정 근거 및 후속 조치 |
| resource | 인력 마스터 | 담당자명 ↔ 소속회사(협력사) 매핑, 조직/협력사 목록 |

### WBS 시트 컬럼 구조 (가장 중요한 시트)

```
ID(WBS 계층번호, 예: 1, 1.1, 1.3.1) | 단계(Phase 일련번호) | 분류(Level1) | 작업(Level2, Task명)
  | Fr/To 점검(O/X, 시작·종료 체크리스트) | 점검대상/점검결과(SKIP/확인대상, 진행중/종료/미도래)
  | 설계여부 | 담당자 | 현업 업무 지원(이해관계자) | 점검사항(비고)
  | 시작일(계획) | 완료일(계획)
  | 목표공정율(%) | 공정율(%)(수동입력, 실적)
  | [주 단위 진행률 타임시리즈 — 2018-12-03부터 매주 한 컬럼, 각 주차 시점의 누적 진행률을 기록해 그래프를 그림]
```

관찰된 특징:
- **계층형 WBS 번호 체계**(`1.3.1`처럼 outline 넘버링)와 **분류(대분류)/작업(소분류) 2단 텍스트**가 같이 존재 — 즉 트리 구조 + 라벨이 이중으로 관리됨.
- **계획 대비 실적**을 계획일/실적일, 목표공정율/실제공정율로 항상 쌍으로 관리.
- **진행률의 시계열 스냅샷**(주간)을 컬럼으로 쌓아서 번-차트/그래프를 자동 생성 — 이건 "지금 몇 %"뿐 아니라 "언제 얼마나 올라갔는지" 이력이 요건이라는 뜻.
- 상위 항목(예: `1.3 인프라 구축(개발)`)의 공정율은 하위 항목들의 가중평균으로 보임(값이 하위 항목 평균과 비슷하게 움직임) — **집계는 상향식(bottom-up) 자동 계산**이며, 아래 3절에서 이 방향으로 확정됨.
- `담당자` 값이 `resource` 시트의 이름과 일치 → 인력 마스터와 연결됨.
- `현업 업무 지원`처럼 프로젝트 조직 바깥의 이해관계자(고객사 담당자) 연락처도 태스크 단위로 남김.
- 상태값이 `진행중 / 종료 / 미도래` 등 정해진 코드 집합.

## 2. 사용자가 원하는 확장 (요구사항 요약)

> "사업 전 RFP > 제안서 > 요구사항 정의서 순으로 나오는 문서들이 관리되어져 WBS의 형태로 나오게 관리가 되어지는 시스템"

즉 이 WBS 문서 하나만 관리하는 게 아니라:

1. **사업 이전 단계(Pre-sales) 문서 파이프라인**: RFP 접수 → 제안서 작성 → (수주) → 요구사항 정의서 확정
2. 이 파이프라인의 산출물(특히 요구사항 정의서)이 **WBS의 작업(Task) 항목으로 이어지는 것**
3. 마일스톤 시트에 이미 나타난 "요구사항 1차/2차/3차" 같은 **문서/요구사항이 버전을 거쳐 정련되는 흐름**까지 시스템이 추적

3절(질문 답변)에서 범위가 **일정관리를 넘어 이슈/리스크/비용/산출물 관리까지(러프하게라도)** 포함하는 것으로 확장 확정됨.

## 3. 확정된 방향 (v1 기준, 질문 답변 반영)

### 3.1 범위 — "다 포함, 단 러프하게"

1차 목표를 WBS+문서 파이프라인으로 좁히지 않고, **이슈관리 / 리스크관리 / 비용관리 / 산출물(성과물) 관리를 모두 v1 범위에 러프하게라도 포함**한다. 각 영역을 완벽하게 구현하기보다 "PM이 프로젝트 하나를 통으로 관리할 수 있는 최소 기능 세트"를 먼저 갖추고, 이후 단계에서 깊이를 더한다.

→ 이 결정에 따라 도메인 후보에 `Issue`, `Risk`, `Budget/Cost`, `Deliverable`이 추가됨(4절 참고).

### 3.2 요구사항 ↔ WBS 연결 — 자동/반자동 기본, 수동 허용

요구사항정의서의 개별 `Requirement` 항목을 저장하면 **기본적으로 WBS 태스크가 자동/반자동으로 생성**되는 흐름을 기본값으로 하되, PM이 요구사항과 무관한 태스크(내부 관리 업무 등)를 **수동으로 직접 추가**하는 것도 항상 가능해야 한다.

→ `Requirement`와 `WbsTask`는 N:M이 아니라 **1(Requirement) : N(WbsTask), 단 WbsTask.requirementId는 nullable**인 구조가 자연스러워 보임(수동 생성 태스크는 연결 요구사항 없음). 반자동 생성의 "생성 규칙"(요구사항 하나당 태스크 1개 생성? 템플릿 기반으로 여러 개 생성?)은 후속 설계에서 구체화 필요.

### 3.3 진행률 집계 — 상향식 가중평균 자동 계산 + 텔레그램 실적 입력(검토 필요)

- 상위 태스크의 진행률은 **하위 태스크의 가중평균으로 시스템이 자동 계산**한다 — 원본 WBS 파일에서 관찰된 동작과 일치. 리프 태스크(하위가 없는 최말단 태스크)만 담당자가 실적을 직접 입력하고, 그 위 단계는 전부 자동 롤업.
- 실적 입력은 원칙적으로 **PMS 화면에서 담당자 본인이 입력**.
- **[논의 필요/가능성 검토]** 업무 시작·마감이 도래하면 **텔레그램으로 담당자에게 알림을 보내고, 그 알림(메시지) 안에서 바로 실적(진행률)을 입력**할 수 있게 하고 싶다는 요구. 기술적으로는 Telegram Bot API의 인라인 키보드(inline keyboard)나 봇과의 DM 답장을 웹훅으로 받아 처리하는 방식으로 가능하나, **PMS 로그인 사용자 ↔ 텔레그램 chatId 매핑**, 보안(사칭 방지), 실적 입력 UX(퍼센트를 어떻게 메시지로 받을지) 등 세부사항은 별도로 논의 필요. 아래 3.6에 별도 정리.

### 3.4 멀티 프로젝트 — 기본 전제

한 테넌트(회사) 안에서 **여러 사업(Project)을 동시에 운영**하는 것이 기본 전제. PMS 화면은 항상 "지금 보고 있는 Project"를 선택한 상태로 동작해야 한다(기존 프레임워크의 "테넌트 컨텍스트"와 유사하게, 이번엔 "프로젝트 컨텍스트"가 하나 더 필요해짐 — 4.5절 참고).

### 3.5 담당자 계정 — 전원 계정 부여(협력사 인력 포함)

**로그인 계정이 없는 인력을 남겨두지 않는다** — 실적 입력은 반드시 담당자 본인이 하므로, 자사 인력뿐 아니라 **협력사(외주) 인력까지 전부 PMS 계정을 부여**한다. `resource` 시트에 있던 "소속회사"(협력사) 정보는 계정 속성으로 이어져야 한다.

→ 기존 `module-user`의 `User`가 "자사 로그인 사용자" 개념에 가깝다면, PMS에서는 **소속 구분(자사/협력사) + 소속회사명**을 가진 사용자 전체가 프로젝트 멤버가 될 수 있어야 함. `User`를 그대로 확장할지, PMS 전용 프로필을 얹을지는 4.5절에서 다룸.

### 3.6 뷰(간트/캘린더) — v1은 목업만, API 연동 없음

간트차트/캘린더 시각화는 v1 범위에 포함하되, **이번 단계에서는 실제 데이터 연동 없이 목업(화면/레이아웃)까지만** 진행한다. 실제 데이터 바인딩은 이후 단계 과제로 남긴다.

### 3.7 로그인 첫 화면 — 개인화 To-Do 대시보드

각 사용자가 로그인하면 **첫 화면에 본인에게 할당된 업무의 To-Do 리스트**가 보여야 한다. "업무 관리에 용이한 기능"이라는 표현대로, 이 대시보드가 PMS의 실질적인 진입점 역할을 하는 것으로 이해됨(구체적 위젯 구성은 후속 논의 — 예: 오늘 마감 임박 업무, 지연된 업무, 최근 배정된 업무, 참여 중인 프로젝트 목록 등 후보).

→ 기존 `module-portal`의 `HOME` 어플리케이션(현재는 기존 `DashboardPage` 재사용 중)을 PMS 전용 대시보드로 교체하거나, PMS 전용 Application을 새로 만들고 그 안에 To-Do 화면을 넣는 두 가지 방식이 가능 — 후속 논의.

### 3.8 텔레그램 연동 — 선택 기능(optional), 망분리 사업 대응

**"망분리 사업"**(고객사 내부망이 외부 인터넷과 분리되어 PMS 접속 자체가 어려운 환경)에서도 실적 관리를 이어갈 수 있도록, **텔레그램 연동을 옵션 기능**으로 둔다. 즉:

- PMS 자체는 항상 웹 기반으로 정상 동작
- 텔레그램 연동은 **프로젝트 단위(또는 사용자 단위) 설정으로 켜고 끌 수 있는 부가 기능**으로 설계 — 망분리 환경이 아닌 일반 프로젝트에서는 안 써도 무방
- 3.3에서 언급한 "업무 도래 알림 + 알림 내 실적 입력"이 이 기능의 핵심 시나리오

### 3.9 v0.3 확정 사항 (5절 질문 답변 반영)

#### 3.9.1 요구사항 → WBS 태스크 생성: 단계별 템플릿으로 여러 건 생성 (확정)

요구사항 1건을 저장하면 **단계별 템플릿(예: 분석 → 설계 → 개발 → 테스트)에 따라 여러 개의 태스크가 생성**된다.

- `WbsTemplate` / `WbsTemplateItem`: 템플릿 마스터와 단계 항목(단계명, 순서, 기본 소요일수 또는 가중치). 테넌트 단위로 관리하고, 프로젝트 생성 시 기본 템플릿을 선택하거나 요구사항 유형별로 다른 템플릿을 지정할 수 있게 한다.
- 생성 구조(v0.5 수정): 원본 WBS(상세일정계획 v2.1)처럼 **Level1 = 단계(사업관리/분석/설계/개발/테스트/이행/준공·안정화, 단계별 가중치), Level2 = 분류(그룹웨어/협업/ECM/SSO/포탈 등), Level3 = 작업**으로 트리를 구성한다. 요구사항(기능) 1건은 **분석·설계·개발·테스트 각 단계의 해당 분류 아래에 리프 태스크를 하나씩 생성**한다(예: 「전자결재」 → 분석 > 그룹웨어 > 전자결재 분석, 설계 > 그룹웨어 > 전자결재 설계 …). 즉 기능 관련 업무는 반드시 4개 단계에 모두 포함된다.
- **선행 순서 규칙**: 같은 기능의 업무는 분석 → 설계 → 개발 → 테스트 순으로만 진행된다(`predId`, finish-to-start). 선행 업무가 100%가 아니면 후행 업무는 진척률을 입력할 수 없고(0% 고정), 계획 일정도 선행 종료일 다음 영업일부터 시작하도록 생성한다. 단계 전체는 기능별로 어긋나게 겹칠 수 있다(원본 WBS도 설계와 구현이 겹침). 
- 기능 전체 진척은 단계 비율(분석 10 / 설계 20 / 개발 50 / 테스트 20)로 가중평균하며, 화면에는 「단계별 트리」(원본 WBS 방식)와 「기능 × 단계」 매트릭스 두 가지 보기를 제공한다.
- 단계/분류 상위 노드는 하위 리프의 가중평균으로 자동 집계된다(3.3). 단계말 검토(분석/설계/개발/테스트)는 기능 업무와 별개의 수동 태스크로 둔다.
- 생성된 태스크의 일정/담당자는 비어 있거나 기본값으로 만들어지고, PM이 이후 채운다(반자동). 수동 태스크 추가는 계속 가능하다(3.2).
- **v0.4 확정**: 기본 단계는 **분석 / 설계 / 개발 / 테스트 4단계**이며, 요구사항 유형별 템플릿은 두지 않는다(현재 템플릿 1종). 템플릿 마스터 구조(`WbsTemplate`)는 향후 확장을 위해 유지하되 v1 화면에서는 단일 템플릿만 노출한다.
- 후속 설계 필요: 요구사항 수정/삭제 시 이미 생성된 태스크의 처리(재생성 vs 유지), 템플릿 변경이 기존 태스크에 소급되는지 여부(원칙: 소급하지 않음).

#### 3.9.2 담당자: 업무당 1인, 복수 필요 시 업무 복사 (확정)

`WbsTask`의 담당자는 **정확히 1명**(`assigneeId`)이다. 별도의 `TaskAssignment`(N:M) 엔티티는 두지 않는다 — 진척률의 책임 소재를 명확히 하기 위한 결정.

- 여러 명이 같은 업무를 해야 하면 **업무를 복사**해서 사람마다 태스크를 하나씩 갖는다. 복사 기능(`copy`)은 PM이 담당자만 바꿔 쉽게 복제할 수 있는 1급 기능으로 제공한다(제목/일정/요구사항 연결/상위 태스크는 그대로, 진척률은 0으로 초기화).
- 복사본끼리의 관계 추적용으로 `copiedFromTaskId`(nullable)를 둔다 — 보고서에서 "원본 업무 단위"로 묶어 볼 수 있게 하기 위함이며, 진척 집계에는 영향이 없다.
- 주의: 복사본은 상위 태스크 가중평균에 각각 하나의 태스크로 반영되므로, 사람 수만큼 가중치가 늘어나지 않도록 **복사 시 가중치를 분할**한다. **v0.4 확정: 균등 분배** (원본 가중치 ÷ 복사본 포함 총 개수. 별도 옵션 없음).

#### 3.9.3 이슈/리스크/비용/산출물 연결 구조 (확정 — v0.4 승인)

**제안: 모두 Project 하위 공통 엔티티로 두고, 필요한 것만 태스크 등에 선택적으로 연결(nullable)한다.**

| 엔티티 | 필수 연결 | 선택 연결 | 이유 |
|---|---|---|---|
| `Issue` | `projectId` | `taskId`, `milestoneId` | 이슈는 프로젝트 단위 목록/통계가 기본 보기이고, 특정 업무에서 발생했을 때만 태스크를 연결해 추적 |
| `Risk` | `projectId` | `taskId`(관련 업무, 선택) | 리스크는 본래 프로젝트 레벨 개념이라 태스크 연결은 참고용 |
| `Deliverable` | `projectId` | `taskId` 또는 `milestoneId` | 산출물은 단계/마일스톤 완료 조건이 되는 경우가 많아 연결 가치가 큼 |
| `Budget`/`Cost` | `projectId` | 없음 (공수 → 비용 환산은 `ResourcePlan`/실적에서 계산) | 비용을 태스크 단위로 직접 입력받으면 입력 부담이 커지고 인력 공수와 이중 관리됨 |

- 이유 요약: (1) 항상 프로젝트 목록 화면이 먼저 필요하고, (2) 태스크 연결을 필수로 하면 "태스크가 정해지기 전 발생한 이슈/리스크"를 등록할 수 없으며, (3) 연결을 선택으로 두면 나중에 추가해도 데이터 구조 변경이 없다.
- 태스크 상세 화면에서는 연결된 이슈/산출물을 탭으로 보여준다(역방향 조회).

#### 3.9.4 협력사 계정 등록: PM 직접 생성 + 셀프 가입 모두 지원 (확정)

- **PM 직접 생성**: PM이 프로젝트 멤버 화면에서 협력사 인력을 바로 만든다(소속구분/소속회사 포함). 기존 `UserController`의 관리자 생성 경로와 동일한 패턴.
- **셀프 가입**: 프로젝트 **초대코드/링크**로 가입 화면에 진입해 본인이 소속회사 등을 입력한다. 가입 직후에는 **승인 대기** 상태이며, PM이 승인해야 해당 프로젝트에 접근할 수 있다(사칭/무단 가입 방지).
- **v0.4 확정**: 초대코드는 **프로젝트 단위**로 발급하고 **유효기간은 1개월**이다(만료 후 PM이 재발급).
- 기존 회원가입(`/api/v1/auth/register`)의 `defaultYn=Y` 그룹 자동 배정과 맞춘다 — 협력사용 기본 UserGroup(최소 권한)을 별도로 두고, 프로젝트 참여 권한은 `ProjectMember`로 관리한다(4.5).

#### 3.9.5 메신저 연동: 텔레그램 + Mattermost 모두 v1 포함 (확정)

- 텔레그램 연동(3.8)은 v1 범위에 포함하고, **Mattermost 연동도 함께** 구현한다. Mattermost는 고객사 내부망에 설치할 수 있어 망분리 사업에 더 적합하다.
- 구현은 **알림 채널 추상화**로 한다: 발송(오늘 할일/마감 알림), 콜백 수신(진척률 입력), 사용자 매핑을 인터페이스로 정의하고 텔레그램/Mattermost를 각각 구현체로 둔다. 프로젝트 단위로 사용 채널을 선택한다(미사용도 가능).
- **v0.4 확인**: Mattermost는 **고객사 기존 서버를 사용**한다(신규 설치 아님). 남은 확인: PMS ↔ Mattermost 서버 간 네트워크 경로(Mattermost → PMS 콜백 가능 여부), 봇 계정 발급 권한, 사용자 매핑 키(loginId vs 이메일).
- 알림 안에서의 진척률 입력은 인라인 버튼(텔레그램) / Interactive Message 버튼(Mattermost)으로 단계 선택(0/25/50/75/100%)을 기본으로 하고, 임의 값 입력은 슬래시 커맨드 또는 다이얼로그로 지원한다. 입력은 **리프 태스크의 담당자 본인**만 가능하다(3.3, 3.9.2).

### 3.10 프로젝트(사업) 관리 — 항목 및 상태 정의 (v0.6, 화면 목업 기준)

영업(수주 전)부터 수행·종료까지를 **하나의 프로젝트 레코드**로 관리한다(수주 후 같은 프로젝트에 WBS가 이어짐).

**상태(10종)** — 영업 → 수주 → 수행 → 종료 흐름, 상태별 수주 확률도 기본값을 자동 제안(직접 수정 가능)

| 단계 | 상태 | 확률 기본값 | 설명 |
|---|---|---|---|
| 영업 | 공고 전 | 10% | 사전 영업, 발주 정보 수집 |
| 영업 | 공고 중 | 20% | 입찰 공고 게시, 참여 판단·RFP 분석 |
| 영업 | 제안 중 | 30% | 제안서 작성 (제안 마감일 전) |
| 영업 | 평가 중 | 50% | 제안 제출 완료, 발표·평가·결과 대기 |

### 3.11 RFP 관리 / RFP 평가 (v0.7, RFP 관리 화면 목업 완료 · 평가 화면은 후속)

**메뉴 구성**: 영업단계(프로젝트 관리, RFP 관리, [예정] RFP 평가, [예정] 제안서 관리) / 수행 단계(내 업무 대시보드, WBS·진척 관리). RFP·제안서는 프로젝트와 수명 주기·사용자·데이터 단위가 달라 프로젝트 관리와 **별도 메뉴**로 둔다.

**데이터 구조**: 프로젝트 1 : N RFP(차수/재공고) → RFP 1 : N 항목(세분화된 요구사항) → 항목 1 : N 평가(평가자별).

**RFP 관리 (목업 완료)**
- RFP 등록: 프로젝트 연결, RFP명, 차수, 접수일, 제출 마감일, 원본 문서 업로드(pdf/hwp/docx/xlsx).
- 항목 정리 방식: **엑셀 템플릿 업로드(기본)** / 수동 입력 / 문서 자동 분해(추후).
- 항목: 발주사 원문 분류(SFR 기능, PER 성능, SER 보안, ECR 장비, DAR 데이터, QUR 품질, COR 제약, PMR 관리, PSR 지원), 영역, 항목코드(분류-일련번호 자동), 항목명, 요구사항 원문, 원문 페이지, 필수/선택.
- **평가자 지정**: 수행 조직 PM을 1명 이상 지정(1명도, 여러 명도 가능).
- RFP 상태는 계산값: 접수(항목 없음) → 항목 정리 중(평가자 없음) → 평가 중 → 평가 완료. 평가 진행률 = 평가 완료 수 ÷ (항목 × 평가자).

**RFP 평가 / RFP 평가 관리 (v0.8, 목업 완료)** — 영업단계 메뉴: 프로젝트 관리, RFP 관리, **RFP 평가**, **RFP 평가 관리**, [예정] 제안서 관리
- **블라인드 확정**: 평가자는 다른 평가자의 평가를 볼 수 없다. 「RFP 평가」에는 본인 평가만 나오고, 「RFP 평가 관리」에는 **제출 완료된 평가만** 평가자별로 표시한다(작성 중 초안은 비공개).
- **RFP 평가(평가자 화면)**: RFP 관리처럼 항목을 분류별로 열거하고, 항목마다 **기능/비기능 구분**, (기능) **구현 여부**(구현/일부 구현/미구현/협의 필요), **구현 시 예상 M/D**, 의견을 입력한다. 구현·일부 구현이면 M/D 필수, 미구현은 0, 비기능은 M/D 없음. 모든 항목을 입력해야 **평가 제출**할 수 있고, 제출 후에는 수정 불가(평가 관리자가 재평가 요청으로 해제).
- **RFP 평가 관리(평가 관리자 화면)**: 항목을 열거하고 **평가자별 열**로 평가 현황(구분 · 구현 여부 · M/D)을 나란히 보여준다. 평가자별 제출 현황·입력 진행, 구분이 평가자마다 다른 항목은 「구분 상이」로 표시한다.
- **M/D 취합 규칙 없음(확정)**: 평균·최댓값·리더 확정 같은 자동 계산을 두지 않고, 평가자별 값만 보여준다.
- **소계·총합**: 분류(구분)별 **M/D 소계**를 각 분류 아래에, **M/D 총합**을 표 최하단에 평가자별로 표시한다(기능 항목 기준). 총합 아래에 기능/비기능 항목 수도 표시. ※ "구분"을 RFP 원문 분류(SFR 등)로 해석해 구현했다 — 기능/비기능 기준 소계가 필요하면 추가 가능.
- **난이도(v0.9)**: 평가자가 항목마다 **난이도(하/중/상)**를 입력한다. 기능 항목은 필수(구현 여부와 함께 입력 완료 조건), 비기능은 선택. M/D에 자동 반영하지 않고 참고 정보로 평가 관리 화면에 평가자별로 표시한다.
- **소계 기준 확정(v0.9)**: 소계는 RFP 원문 분류(SFR/PER/SER …)별로 낸다.
- 후속: 프로젝트 예상 원가 연계(아래 3.12), 수주 후 확정된 기능 항목 → 요구사항 → WBS(3.9.1) 연결.

### 3.12 제안서 관리 (v0.9, 목업 완료) / 예상 원가 연동 (설계안)

**제안서 관리 (목업 완료)**: 프로젝트 1 : N 제안서(RFP별) → 제안서 1 : N 버전 / RFP 항목 대응표 / 제출 체크리스트.
- 제안서: 프로젝트·대응 RFP 연결, 작성 책임자, 상태(작성 중 → 내부 검토 → 제출 완료 → 결과 확정), 제출 마감일(D-day), 제출일, 제안 금액, 예상 원가 → 예상 이익률.
- **버전 이력**: 버전별 파일·작성자·변경 요약 보관, 제출본 표시.
- **RFP 항목 대응표**: RFP 항목마다 제안서 목차(절), 대응 방식(수용/일부 수용/대안 제시/미수용), 대응 요약, 담당자를 입력. 대응 완료 수와 **필수 항목 미대응 건수**를 상단에 표시해 누락을 점검. 제출 완료 후에는 수정 불가.
- **제출 체크리스트**: 제출 서류(본문, 요약본, 가격 제안서, 인증서, 위임장, 발표 자료 등) 준비 현황.

**예상 원가 연동 (설계안, 구현 전)**
1. 원가 산정용 **확정 M/D**: 평가자별 값은 자동 취합하지 않으므로, 평가 관리자가 항목별 확정 M/D를 정하는 단계를 둔다(일괄 채우기 보조: 특정 평가자 값 / 평균 / 최댓값 — 입력 보조일 뿐 규칙이 아님).
2. **M/D 단가**를 프로젝트(또는 RFP) 단위로 설정(등급별 단가 확장 가능) → 확정 M/D 합계 × 단가 = 직접 인건비. 간접비·가산율은 옵션.
3. 결과를 프로젝트 관리의 **예상 원가**와 제안서의 예상 원가·이익률에 반영(출처 표시 + 수동 수정 허용).

### 3.13 문서 테일러링 / 단계말 산출물 관리 (v1.0, 목업 완료)

메뉴: 수행 단계 폴더의 **첫 메뉴 = 문서 테일러링 관리**, 이어서 내 업무 대시보드, WBS·진척 관리.

**문서 테일러링 관리**
- 단계(분석·설계·개발·테스트)별 **표준 산출물 목록**(문서 종류, 표준 필수/권장)에서 프로젝트에 적용할 문서를 정한다 — **적용 / 미적용**.
- **미적용은 사유 필수**. 표준 필수 산출물을 제외하면 경고(발주사 합의 필요)를 표시하고, 필수 제외 건수·사유 미입력 건수를 상단에 집계.
- 담당자 지정, 프로젝트 고유 **문서 종류 추가/삭제**, 표준 목록으로 초기화. 제출 시점은 「해당 단계 단계말 검토」로 고정.
- 이행 단계 문서는 후속(WBS 단계말 검토가 있는 4개 단계만 대상).

**WBS·진척 관리 — 단계말 산출물**
- WBS의 **단계말 검토** 행에 **📄 산출물 n/m** 버튼(등록 수 / 적용 문서 수)을 두고, 누르면 해당 단계 **적용 문서만** 대상으로 관리 화면이 열린다.
- 기능: **등록 / 새 버전**(v1.0, v1.1 … 자동 채번), **수정**(최신 버전 파일 교체·비고), **다운로드**, **삭제**(최신 버전), **검토 완료/해제**, **버전 이력**. 상단에 등록 현황·검토 완료·필수 산출물 미등록 건수 표시.
- 테일러링에서 제외한 문서는 사유와 함께 별도 표시. 상태: 미등록 → 등록 → 검토 완료.
- 후속 검토: 필수 산출물 전부 등록 시 단계말 검토 업무 진척 자동 반영, 검토/승인 권한(PM·고객사 열람자), 실제 파일 저장(`module-file` 연동).

### 3.14 이슈 관리 + WBS 양방향 연결 (v1.1, 목업 완료)

수행 단계 메뉴: 문서 테일러링 관리, 내 업무 대시보드, WBS·진척 관리, **이슈 관리**. 이슈는 3.9.3대로 프로젝트 공통 엔티티이며 **WBS 업무(taskId)는 선택 연결**(업무 1건 : 이슈 N건, 이슈 1건 : 업무 0~1건)이다.

**이슈 항목**: 제목, 유형(일정/범위·요구사항/품질/인력·자원/기술/고객·협의/기타), 우선순위(긴급/높음/보통/낮음), 상태(오픈 → 진행 중 → 해결 → 종결), 담당자, 보고자, 조치 기한, 일정 영향(일), 연결 업무, 내용, 조치 내용(해결·종결 시 필수), **처리 이력**(등록·상태 변경·업무 연결/해제는 자동 기록 + 메모 추가).

**이슈 관리 화면**: 집계(미해결, 긴급·높음 미해결, 조치 기한 초과, 업무 미연결, 미해결 일정 영향 합계), 상태 칩, 검색·우선순위·유형·담당자·업무 연결 여부 필터, 목록에서 등록·수정. 연결 업무 옆 **「WBS ›」**로 WBS의 해당 업무로 이동(트리를 펼치고 행 강조).

**WBS·진척 관리 화면 (업무 → 이슈)**
- 업무 행에 **⚠ 이슈 미해결/전체** 버튼 — 그 업무의 이슈 조회, **이 업무에 이슈 등록**, **기존 이슈 연결**(미해결 이슈 선택), **연결 해제**, **이슈 관리에서 열기**.
- 업무명 옆 이슈 배지(긴급·높음 미해결이면 빨강, 미해결이면 주황, 모두 해결이면 초록). **상위 행(분류·단계)의 배지는 하위 업무 이슈의 합계**.

**프로젝트 조회 범위(v1.9)**: 이슈는 프로젝트(`projectId`)에 속하고, 이슈 관리의 검색 조건에 **프로젝트 선택**이 있다. 일반 사용자는 **내가 참여 중인 수행 프로젝트**(프로젝트 관리자·투입 인력·영업 담당·수행 PM)의 이슈만, **센터장·admin(ROLE_CENTER_HEAD / ROLE_ADMIN / ROLE_SYSTEM_ADMIN)은 수행 중인 전체 프로젝트**의 이슈를 본다. 목록에 **프로젝트명** 컬럼을 표시하고, 이슈 등록 시 프로젝트를 필수로 선택(연결 업무는 해당 프로젝트 WBS에서만 선택).

**후속 검토**: 이슈 1건을 여러 업무에 연결(영향 범위), 이슈 해결 시 업무 일정 자동 조정 제안, 내 업무 대시보드에 담당 이슈 표시, 이슈 삭제·권한 정책, 리스크/산출물 관리와의 연계.

### 3.15 주간 보고 / 월간 보고 (v1.2, 목업 완료)

수행 단계 메뉴: …, 이슈 관리, **주간 보고**, **월간 보고**. 같은 화면 구성을 기간 단위(주/월)만 바꿔 쓴다.

**구성**: 로그인 사용자가 **참여한 프로젝트별**(수주·수행 중이면서 영업 담당 / 수행 PM / 내 업무 보유) 보고 블록을 세로로 나열(프로젝트 칩으로 필터).
- **좌측 — 현재 진행 중인 업무**: 해당 기간까지 착수했고 미완료인 업무(지연·선행 대기 표시, 지연 우선·기한순), 담당·기한(D-day)·**진척률**.
- **우측 — 다음 주(달) 업무**: 다음 기간에 수행·기한이 걸린 미완료 업무를 **기한(D-day)**과 함께, 신규 착수/계속 구분.
- **하단 — 금주(당월) 해결한 이슈 / 현재 진행 중인 이슈**: 해결일이 기간 내인 이슈와 미해결(오픈·진행 중) 이슈(우선순위·상태·담당·조치 기한).
- 데이터 출처: WBS 업무(진척·일정)와 이슈 관리. 업무별 진척률은 **조회 시점 기준**.
- **진척 스냅샷(v2.6, 목업)**: 프로젝트별로 매주 월요일 기준 전체 진척(실적)·목표를 저장한다(「스냅샷 저장」, 같은 주는 덮어쓰기). 보고서에 **기간 진척 증감(%p, 계획 증감 병기)** 과 **실적/목표 추이 차트**를 표시하고 보고 내용 복사에도 포함한다. 스냅샷이 없는 기간은 증감을 표시하지 않는다. 자동 저장(스케줄러)·번다운·업무 단위 스냅샷은 후속.

**추가 반영한 제안 기능**
- 프로젝트 요약 KPI: 전체 진척·계획 대비(%p), 금주 완료 업무, 지연 업무, 미해결 이슈(긴급·높음), 금주 신규 이슈.
- 기간 이동(이전/다음)·이번 주/달로 복귀, **내 업무·이슈만 보기** 토글.
- **특이사항·요청사항** 입력란(보고서에 포함), **보고 내용 복사**(메일·메신저용 텍스트), 엑셀/PDF 내보내기(목업).
- 월간: 단계별 진척(실적/목표) 막대.

**후속 제안**: 진척 스냅샷 기반 기간 증감(주간 진척 +n%p), 보고서 작성 → 제출 → 확정 상태·이력 보관, 발주사 공유용 보고서 양식(고객사 열람자 역할), 단계말 산출물 등록 현황·리스크 항목 포함, 보고 자동 알림(텔레그램·Mattermost로 보고 초안 전송), 인력 투입(M/M) 실적 포함.

### 3.16 단계전환 (수주 → 수행, v1.3 목업 완료)

**메뉴 구조(PMS)**: 영업단계(프로젝트 관리, RFP 관리, RFP 평가, RFP 평가 관리, 제안서 관리) → **단계전환(신규 폴더) > 단계전환** → 수행 단계(문서 테일러링 관리, WBS·진척 관리, 이슈 관리, 주간 보고, 월간 보고, **내 업무 대시보드 = 수행 단계 맨 아래**).

**목적**: 수주가 확정된 프로젝트를 수행 단계로 넘기면서 수행 단계의 **기초데이터(문서 테일러링 / WBS·진척 관리)**를 자동 생성하고, 프로젝트 상태를 `수주 → 수행 중`으로 전환한다.

**화면 흐름**
1. **전환 대상 목록**(상단): 상태가 「수주」이고 아직 단계전환하지 않은 프로젝트(RFP·항목 수, 평가자 수 표시) → 선택.
2. **프로젝트 단계 선택**: 분석 / 설계 / 개발 / 테스트 중 수행할 단계(일부만 선택 가능).
3. **RFP 항목 선택**: 해당 프로젝트에 등록된 RFP의 항목을 분류별로 나열(분류 단위 일괄 선택, 전체/기능만/필수만/해제). 제출된 RFP 평가를 요약해 구분(다수결)·평균 M/D·난이도·제출 현황을 참고값으로 표시. 기본 선택은 비기능으로 평가된 항목을 제외한 항목.
4. **프로젝트 관리자 · 투입 인력 선택 (v1.5 재정리)**
   - **프로젝트 관리자(1명, 필수)**: 문서 테일러링·WBS/진척 관리 등 **수행 단계의 기본 정보를 관리**하는 사람. 프로젝트 내 역할은 **PM / PL / PMO** 중 하나(컨소시엄·파트 계약에서는 PL 또는 PMO가 관리자가 될 수 있다). 사업관리·단계말 검토 업무의 담당이 된다. 역할이 PM이면 프로젝트 수행 PM으로도 기록.
   - **투입 인력(1명 이상, 추가 방식)**: 인력마다 **프로젝트 내 역할**(PL, 분석, 설계, 분석/설계, 개발, DBA, UI/UX, QA, TA, PMO, 기타), **투입 단계**(분석/설계/개발/테스트, 전체 가능), **투입 M/M**, **투입 기간(FROM ~ TO)**을 지정(v1.6). M/M·기간은 **이후 인력관리(투입관리)의 기준 데이터**이며, 기간 기준 M/M(투입률 100%) 제안 버튼과 프로젝트 기간 밖 경고를 제공. 한 사람은 한 번만 추가하되 **프로젝트 관리자도 투입 인력에 포함 가능**.
   - **WBS 반영(v1.6)**: 그 단계에 투입된 **인력 전체**에게 업무를 배분한다(업무당 담당자 1명). 후보 목록은 단계별 주 역할이 위에 오도록 정렬(개발 단계: 개발 → DBA → UI/UX → TA → PL …, PMO는 다른 인력이 있으면 제외)하고, 배분은 **투입 M/M 비율**(M/M이 없으면 균등)로 한다. 배정 방식: ① 투입 인력 전체 분배(권장) ② 단계 대표 1명(목록 첫 번째) ③ 미배정. **투입 인력이 없는 단계는 프로젝트 관리자에게 배정**.
   - 문서 테일러링의 문서 담당은 단계 대표 인력(없으면 프로젝트 관리자). 화면에 단계별 업무 담당 후보 미리보기를 보여준다.
   - **협력사 인력**: 업무 접근을 제한하는 대신 **내 업무 알림(메신저)을 받고 알림에서 진척·이슈를 처리**한다(관리자가 WBS·이슈 관리에서 대신 입력 가능). 투입 인력에 알림 채널(Mattermost/텔레그램/이메일)을 지정하고 WBS 담당자에 「협력」 표시.
   - 전환 이력에 프로젝트 관리자(역할)와 투입 인원·M/M 합계(역할·단계·기간은 툴팁)를 기록.
5. **미리보기 → 단계전환 실행**: 생성될 WBS 업무 수·예상 기간·문서 테일러링 적용/제외 수를 보여주고 확정.

**생성 규칙**
- **WBS**: 사업관리(착수·착수보고) + 선택 단계를 Level1, RFP 원문 분류를 Level2, 선택한 RFP 항목을 Level3 업무로 생성. 항목마다 **선택한 단계 순서대로 업무 1건씩**(선행 finish-to-start), 업무명 `항목명 + 단계`, 요구사항 코드 = RFP 항목 코드. 소요일 = 항목 평균 M/D × 단계 비율(10/20/50/20, 최소 2일), 가중치 = M/D. 단계말 검토는 단계 마지막 업무 뒤 3영업일, 진척 0%로 시작. 시작일은 프로젝트 시작 예정일.
- **문서 테일러링**: 선택한 단계의 표준 산출물 중 **필수 문서는 적용**, 권장 문서는 선택한 RFP 항목의 분류에 해당할 때만 자동 적용(SER→보안 설계서·보안 취약점 점검 결과서, PER→성능테스트 결과서, DAR→데이터 이관 분석서, QUR→코딩 표준 점검 결과서·사용자 인수 테스트 결과서, SFR→프로그램 설계서). 나머지는 사유("RFP 선택 항목에 해당 분류 없음")와 함께 미적용으로 시작하며 전환 후 수정 가능.
- 프로젝트: 수행 PM 지정, 전환 이력(전환일·RFP·항목 수·단계) 기록. 화면 하단에 단계전환 이력과 WBS·문서 테일러링 바로가기.
- RFP가 없는 수주 프로젝트도 단계·표준 산출물만으로 전환 가능.

**WBS 다중 프로젝트**: WBS·진척 관리에서 WBS가 있는 프로젝트를 선택해 본다(`?project=ID`). 이슈·주간/월간 보고·대시보드도 프로젝트별 업무를 따른다.

**후속 검토**: 소요일을 팀 규모(투입 인원)·일정 제약 기준으로 산정, 전환 시 요구사항 정의서 생성(RFP 항목 → 요구사항 ID 연결), 단계전환 승인 절차, 전환 취소(롤백).

### 3.17 수행 단계 「프로젝트 관리」 (v1.6, 목업 완료)

수행 단계 메뉴: **프로젝트 관리**(신규, 첫 메뉴) → 문서 테일러링 관리 → WBS/진척 관리 → 이슈 관리 → 주간 보고 → 월간 보고 → 내 업무 대시보드. **단계전환에서 지정한 프로젝트 관리자**가 수행 단계의 프로젝트 관리 + 문서 테일러링 + WBS/진척 관리를 맡는다.

- **영업단계 기본 정보(수정 불가)**: 코드·상태·프로젝트명·발주사·발주금액·기간·사업구분·입찰방식·공고번호·발주사 담당자·영업 담당자·대응 RFP·비고. 수정은 영업단계의 프로젝트 관리에서만.
- **수행 관리 정보(수정 가능)**: 단계전환에서 지정한 **프로젝트 관리자(PM/PL/PMO)와 투입 인력**을 그대로 보여주고 수정한다. 투입 인력은 **프로젝트 멤버와 같은 데이터**(역할·투입 단계·M/M·투입 기간·협력사 알림 채널). 수정 권한은 프로젝트 관리자 본인만(그 외 열람만).
- 투입 인력을 바꿔도 이미 생성된 WBS 업무의 담당자는 자동으로 바뀌지 않는다(WBS에서 지정·업무 복사). WBS 업무 복사의 담당자 후보는 프로젝트 관리자 + 투입 인력.
- 요약(투입 인원·자사/협력사·M/M 합계·단계별 투입), 문서 테일러링/WBS 바로가기.

**후속 검토**: 투입 인력 변경 시 미배정/담당자 재배정 제안, 인력관리(투입관리) 메뉴(투입률·기간 충돌·타 프로젝트 겹침), 프로젝트별 접근 권한(멤버 외 열람 제한), 협력사 알림 기반 진척·이슈 입력(메신저 연동).

### 3.18 인력관리 — 투입 관리 (v1.7, 목업 완료)

메뉴: 신규 폴더 **인력관리 > 투입 관리**(PMS 맨 아래). 투입 계획의 원천은 프로젝트의 수행 관리 정보(단계전환에서 지정한 투입 인력 = 프로젝트 멤버: 역할·투입 단계·**M/M·투입 기간**)이고, 투입 관리는 이를 **인력 기준으로 모아** 계획 대비 투입을 관리한다. 계획(역할·단계·M/M·기간) 수정은 수행 단계 「프로젝트 관리」에서만 한다(단일 원천).

**월별 계획 투입률**: M/M ÷ (투입 기간의 월 환산) = 월 투입률(1.0 = 100%), 첫·마지막 달은 걸친 일수만큼 비례. M/M 미입력이면 100%로 가정. 인력별 월 합계가 **105%를 넘으면 과투입**으로 경고.

**탭 구성**
1. **인력별 투입 현황**: 인력 × 12개월 월 투입률 히트맵(3개월 단위 이동), 투입 프로젝트·M/M, 과투입 태그와 경고 목록, 요약(투입 인원, 투입 M/M 합계, 과투입 인원, 당월 여유 인력). 인력을 누르면 프로젝트별 **월 계획 M/M과 실적 M/M(입력)**, 월 합계 투입률 표시.
2. **프로젝트별 계획·실적**: 프로젝트의 투입 인력별 계획 M/M, 실적 M/M, 소진율, 타 프로젝트와 겹쳐 과투입인 달 표시.
3. **가용 인력 조회**: 기간·필요 투입률·직무로 조회 — 기간 내 최대 투입률 기준 여유 투입률과 투입 가능/여유 부족 판정, 해당 기간 투입 프로젝트(제안·수주 단계 투입 인력 검토용).

**실적 M/M**: 월별 입력(과거~당월), 인력 × 프로젝트 단위 누적. **후속 검토**: 실적 입력 주체·마감(월 마감), 업무 진척/공수와의 연계, 협력사 인력 실적 승인, 계획 변경 이력(투입 변경 요청·승인), 직무·등급별 단가로 인건비 환산(예상 원가 연계), 휴가·교육 등 비투입 일정 반영.

### 3.19 투입 관리 결정 사항 반영 (v1.8)

- **실적 M/M 입력**: **프로젝트 관리자가 입력**한다(수행은 수행 관리자, 운영은 운영 관리자). 그 외 사용자는 조회만. 협력사 인력 실적도 관리자가 입력.
- **과투입 기준은 설정으로 변경**: 투입 관리 「⚙ 설정」에서 과투입 기준(월 투입률 %, 기본 105)과 여유 인력 기준(%, 기본 50)을 바꾸면 현황·경고·가용 인력 조회에 즉시 반영.
- **투입 계획 변경 요청 · 승인 · 이력(우선 적용)**
  - 수행 단계 「프로젝트 관리」에서 프로젝트 관리자·투입 인력(역할·단계·M/M·기간)을 바꾸면 **변경 요청**(변경 사유 필수)으로 등록되고, **인력 관리자의 승인 후** 반영된다(승인 전에는 기존 계획 유지, 대기 중에는 수정 불가, 요청자는 취소 가능).
  - 요청서에는 변경 전/후 차이와 **승인 시 과투입 예상**을 보여준다. 승인·반려(반려 사유 필수)·취소는 모두 이력으로 남고, 요청자 본인은 승인할 수 없다.
  - 승인 화면: 투입 관리 > **변경 요청 · 이력**(대기 건수 표시). 단계전환 최초 지정은 승인 없이 반영.
- **비투입 일정(휴가·교육 등)은 제외**. **직무·등급별 M/M 단가와 원가 연동은 TO-DO**(`02-TODO.md`).
- 투입 관리는 수행 중 프로젝트의 수행 인력과 운영 중 프로젝트의 운영 인력을 함께 집계(운영 투입은 「프로젝트명 (운영)」으로 구분).

### 3.20 단계전환 분리(수행/운영) 및 운영 단계 (v1.8, 목업 일부 완료)

**프로젝트 상태 확장**: …→ 수주 → 수행 중 → **수행 종료**(준공/검수 완료, 기존 「완료」) → **운영 중** (실패/보류·취소 별도).

**메뉴(PMS)**: 영업단계 → **단계전환(수행단계전환 / 운영단계전환)** → 수행 단계(프로젝트 관리, 문서 테일러링, WBS·진척, 이슈, 주간·월간 보고, 내 업무 대시보드) → **운영 단계(프로젝트 관리)** → 인력관리(투입 관리).

- **수행단계전환**: 기존과 동일(수주 확정·미전환 프로젝트).
- **수행 종료 처리**: 수행 단계 「프로젝트 관리」에서 프로젝트 관리자가 수행 종료일(준공/검수일)·비고·**운영 인수 대상 기능**(WBS 기능/RFP 항목에서 자동 구성, 수정 가능)을 확정. 미완료 WBS 업무·미해결 이슈 건수 경고. 처리 후 수행 정보는 읽기 전용.
- **운영단계전환**: 대상 = **수행 종료 상태**이면서 아직 운영 전환하지 않은 프로젝트. 흐름: ① 운영 형태(하자보수 / 유상 유지보수 / 하자보수+유지보수)·운영 기간(기본: 수행 종료 다음날부터 1년)·계약금액(옵션)·**SLA**(등급 기본/표준/프리미엄 + 장애 응답·해결 목표 시간, 서비스 시간) ② **인수 대상 선택** — 운영 대상 기능, 인수 산출물(수행에서 등록된 최신 버전), **미해결 이슈 이관** ③ **운영 관리자(1명, 운영 PM/PL/PMO) · 운영 인력**(역할 운영·장애대응·기술지원·DBA·UI/UX·QA·TA·PL·PMO·기타, M/M, 투입 기간; 수행 인력 불러오기 지원). 실행하면 프로젝트가 「운영 중」이 되고 운영 기초데이터가 생성된다.
- **운영 단계 「프로젝트 관리」**: 영업·수행 단계 정보(수정 불가) + 운영 정보(운영 형태·기간·SLA·계약금액, 운영 관리자·인력, 수정은 운영 관리자만) + 인수(이관) 현황(운영 대상 기능·인수 산출물·이관 이슈).

**운영 단계 메뉴 제안(미구현)**
1. **장애·문의 관리**(Incident/Service Request): 접수 → 분석 → 조치 → 종결, SLA 응답·해결 시한(운영 정보의 SLA와 연동), 이관 이슈를 운영 이슈로 승계.
2. **변경 요청(CR) 관리**: 무상/유상 판단, 공수(M/D) 산정, 승인, 처리 이력, 유상이면 청구와 연결.
3. **SLA 관리 · 현황**: 응답·해결 준수율, 위반 건 알림, 월별 추이.
4. **운영 보고**: 월간 운영 보고(장애·문의 통계, SLA, 변경, 점검 결과), 수행 보고 양식과 동일 구조.
5. **정기 점검 · 작업 일정**: 월간 점검, 패치·배포 일정, 점검 결과 기록.
6. **하자보수 관리**: 무상 하자보수 기간·건수·잔여 기간 관리(운영 형태가 하자보수/하자보수+유지보수일 때).
7. **서비스 카탈로그(운영 대상 기능)·인수인계 문서**: 인수한 기능·산출물의 최신본 관리, 운영 매뉴얼·FAQ·지식 베이스.
8. **계약 · 청구 관리**: 유지보수 계약 기간·금액, 월 청구, 계약 만료/갱신 알림, 재계약(운영 종료·갱신) 연계.
9. **운영 인력 투입**: 인력관리(투입 관리)와 연계된 운영 투입 실적(이미 투입 관리에 운영 투입이 집계됨).

**후속 검토**: 운영 정보 변경의 승인/이력 필요 여부, 운영 종료·갱신 상태, 운영 이슈(이관 이슈 + 신규)의 별도 관리.

### 3.21 단가 관리 · 인건비 환산 (v2.0, 목업 완료)

메뉴: **인력관리 > 단가 관리**(투입 관리 아래). 탭 3개.
1. **단가표**: 직무 × 등급(특급/고급/중급/초급)별 **M/M 단가(원)** 와 **적용 기간**(종료일 비우면 계속). 같은 직무·등급의 적용 기간이 겹치면 저장 불가. 단가 인상은 기존 단가를 종료하고 새 단가를 등록(과거 원가 보존). 직무 필터, 현재 적용 중만 보기.
2. **인력 등급**: 인력별 등급 지정(인력 마스터 확장 항목). 등급 미지정·단가 없음 인력을 표시.
3. **프로젝트 원가**: 수행·운영 프로젝트별로 투입 인력의 **월별 계획 M/M × 그 달 적용 단가**를 합산해 예상 인건비 표시(직무별 소계, 발주금액 대비 인건비 기준 이익률, 단가 누락 경고). 「예상 원가에 반영」은 프로젝트 관리 예상 원가에 출처 표시와 함께 반영하는 동작의 목업(실제 반영은 미구현).
- **난이도 가중치**: 설정(기본 꺼짐, 하 0.8 / 중 1.0 / 상 1.3)만 제공. RFP 평가 확정 M/D 단계(3.12)와 함께 적용할 예정이라 현재 투입 기준 원가에는 영향 없음 — **적용 여부는 협의 필요**.
- **예상 원가 반영(v2.5)**: 「예상 원가에 반영」을 누르면 환산 인건비가 프로젝트 관리의 예상 원가에 저장되고 **출처**(기준일·투입 M/M)가 표시된다(기존 값이 있으면 확인, 단가 누락 시 경고). 원가를 수동으로 고치면 출처는 해제된다. 제안서 관리의 예상 원가는 「프로젝트 예상 원가 가져오기」로 같은 값을 쓰고, 이익률도 이 값으로 계산한다.
- 한계: 인력 등급은 단일 값(등급 변경 이력 없음), 간접비·가산율 미반영. 투입 인력이 없는 영업 단계 프로젝트는 환산 불가(RFP 확정 M/D 단계 필요).

### 3.22 고객사 관리 · 고객사 담당자 관리 (v2.1, 목업 완료)

메뉴: PMS 맨 위 신규 폴더 **고객사 관리**(영업단계 이전) > 고객사 관리 / 고객사 담당자 관리. 발주사·담당자를 프로젝트마다 텍스트로 입력하던 것을 **자산(마스터)** 으로 관리한다.
- **고객사**: 코드(CUS-###), 고객사명(필수), 업종, 거래 상태(거래 중/잠재/거래 종료), 사업자번호, 대표 전화, 주소, 홈페이지, 비고. 담당자 수·프로젝트 수 표시, 프로젝트에서 사용 중이면 삭제 불가(거래 종료로 변경).
- **고객사 담당자**: 코드(CTC-###), 고객사(필수), 담당자명(필수), 직책, 부서, 연락처/이메일(둘 중 하나 필수), 사용 여부(퇴사·이동 시 미사용), 비고. 사용 중이면 삭제 불가.
- **프로젝트 관리 변경**: 발주사는 고객사 선택, 발주사 담당자는 선택한 고객사의 담당자 중 선택(직책·연락처·이메일은 읽기 전용 표시). 고객사를 바꾸면 담당자는 초기화. 폼에서 「고객사 등록 / 담당자 등록」은 새 탭으로 열린다. 제안 중 이후 담당자 필수 규칙은 유지.
- 선택 시 이름·연락처를 프로젝트에도 복사해 저장(고객사 정보가 바뀌어도 과거 프로젝트 기록 유지). 후속: 고객사 정보 변경 이력, 영업 활동/미팅 이력, 고객사별 프로젝트 이력 조회.

### 3.23 영업 노트 (v2.2, 목업 완료)

영업단계 첫 메뉴. 영업 담당자의 사전영업·제안 활동을 기록해 **담당자가 바뀌어도 히스토리가 이어지게** 한다(영업일지의 부드러운 이름).
- **노트 항목**: 활동일, 유형(방문/미팅/전화/이메일/식사·접대/제안·발표/자료 전달/정보 수집/인수인계/기타), 프로젝트(선택) 또는 고객사(둘 중 하나 필수 — 프로젝트 등록 전 활동도 고객사만으로 기록), 만난 고객사 담당자, 제목, 내용, 다음 할 일 + 예정일, 작성자.
- **화면**: 요약(전체 노트, 남은 후속 조치, 예정일 초과, 최근 7일 활동), **후속 조치 목록**(예정일순, 초과 강조, 완료 처리), 프로젝트·고객사·작성자·유형·키워드 검색, 최신순 타임라인(행을 누르면 내용 펼침), 수정·삭제.
- **담당자 인수인계**: 영업 진행 중 프로젝트와 인수 담당자를 고르면 활동 히스토리·남은 후속 조치·인수인계 메모를 모은 **요약을 자동 생성**(복사 가능). 처리하면 프로젝트의 영업 담당자가 변경되고 「인수인계」 노트가 자동 기록된다. 기존 기록은 작성자 그대로 유지.
- 후속: 노트 수정·삭제 권한(작성자·관리자), 첨부(명함·메모 사진), 후속 조치 메신저 알림, 고객사 상세에서 히스토리 조회, 인수인계 승인.

### 3.24 운영 업무 · 운영 이슈 · 운영 영업 (v2.3, 목업 완료)

운영 단계 폴더에 메뉴 3개 추가(운영 「프로젝트 관리」 다음). 모두 상단에서 **운영 중인 프로젝트**를 선택해 사용한다(`?project=ID`).
- **운영 업무 관리**: 정기 점검·패치/배포·장애 조치·문의 대응·요청 작업·보고 업무를 등록(업무명·구분·우선순위·담당자·기한·반복·상태·메모)하고 상태를 바로 변경. 요약(전체/진행 중/기한 초과/7일 내 마감/완료), 상태·구분·담당자·검색·내 업무만 필터. 반복(매주/매월/분기)은 표시만 하고 다음 업무 자동 생성은 후속.
- **운영 이슈 관리**: 장애·문의·개선 요청·기타를 접수해 접수 → 분석 → 조치 중 → 해결 → 종결로 처리(해결·종결 시 조치 내용 필수, 응답/해결 시각 자동 기록). 운영 정보의 **SLA 응답·해결 목표 시간**으로 시한을 계산해 충족/정상/임박/위반을 표시하고 SLA 준수율을 집계(장애·문의만 대상, 서비스 시간·휴일은 미반영). 이슈에서 **「업무 등록」**(운영 업무 생성·연결)과 **「영업 기회」**(운영 영업 기회 생성·연결)를 바로 실행.
- **운영 영업 관리**: 재계약·갱신, 추가 개발, 유상 개선, 증설·확장, 교육·컨설팅, 신규 제안 기회를 발굴 → 제안 → 협상 → 수주 / 실패·보류 단계로 관리(예상 금액, 확률도, 담당, 예상 계약일, 다음 할 일). 요약(진행 건수·금액, 가중 예상 금액, 수주 금액, 수주율)과 단계 칩 필터. 운영 종료일이 120일 이내인데 재계약 기회가 없으면 경고와 「재계약 등록」 제공.
- 이관 이슈(운영단계전환 시 이관한 수행 미해결 이슈) 승계, 수주 기회 → 영업단계 프로젝트 자동 생성, 반복 업무 자동 생성은 후속.

### 3.25 차기 사업 기회 관리 (v2.4, 목업 완료)

수행 단계 메뉴: …, 이슈 관리, **차기 사업 기회 관리**, 주간 보고, … 수행 중 고객이 요청했지만 현재 요구사항 범위에 넣지 못한 추가 사항·후속 단계·확산 가능성을 **다음 사업 기회**로 모아 관리한다. 상단에서 수행 중(수행 종료·운영 중 포함) 프로젝트를 선택한다.
- **기회 정보**: 건명, 기회 유형(추가 기능·범위 외 요구 / 후속 단계 / 고도화·개선 / 타 부서·계열사 확산 / 인프라·증설 / 운영·유지보수 전환 / 컨설팅·교육 / 기타), 발생 경로(고객 요청·현장 발견·수행 이슈·영업 제안·기타), **연결 수행 이슈**(고르면 건명·내용 자동 채움), 요구 내용·배경, 현재 범위 외 사유, 우선순위.
- **고객사 담당자**: **요청자**와 **의사결정자**를 고객사 담당자 관리에 등록된 담당자에서 선택(직책·연락처 표시). 의사결정자 미확인 기회는 경고 표시·집계.
- **규모·시기·진행**: 예상 금액, 예상 규모(M/M), 예상 시기(분기), 고객 예산(확보/검토 중/미정), 단계(발굴 → 검토 중 → 제안 준비 → 제안 완료 → 보류/실패 → 이관 완료), 영업 담당자, 다음 할 일·예정일, 비고(보류/실패 사유 필수).
- **화면**: 요약(진행 중 기회, 예상 금액 합계, 예상 규모, 의사결정자 미확인, 운영 영업 이관), 단계 칩·유형 필터.
- **운영단계전환 연결**: 운영단계전환의 「인수 대상 선택」에 **차기 사업 기회 이관** 항목 추가(진행 중 기회 기본 전체 선택, 선택 해제 가능). 실행하면 선택한 기회가 **운영 영업 관리의 영업 기회**로 생성되고(유형 매핑, 요청 담당자·금액·예상 시기·다음 할 일 승계, 출처 「수행 단계 NB-###」 표시) 수행 쪽 기회는 「이관 완료」가 되어 운영 영업 기회 번호를 남긴다. 선택하지 않은 기회는 수행 단계에 남는다. 운영 영업 기회에도 고객사 담당자 필드를 추가했다.
- 후속: 기회 단위 첨부(제안 자료), 이관 기회의 수주 → 영업단계 프로젝트 자동 생성, 운영 영업 → 수행 단계 기회 역조회.

### 3.26 ERD 전 구조 확정 목업 (v2.7, 2026-10-22)

ERD 변경을 줄이기 위해 데이터 구조에 영향을 주는 결정을 목업에 먼저 반영했다.
1. **이슈 1건 : 업무 N건** — 이슈 폼에서 업무를 여러 건 추가/제거, 목록·WBS 이슈 모달·보고서가 N건 기준(WBS 상위 행의 이슈 집계는 이슈 1건을 1건으로 센다). 데이터: `issue_task`(이슈ID, 업무ID) 매핑 테이블, `issue.task_id` 제거.
2. **보고서 작성·제출·수정·재제출** — 주간/월간 보고서를 (프로젝트, 주간/월간, 기간 시작일) 단위 1건으로 저장. 상태 작성 중 → 제출 완료 → (수정 사유 입력) 수정 중 → 재제출(버전 증가), 제출 시점 요약(진척·특이사항)을 버전으로 보관, 모든 상태 변경 이력. 제출 후에는 수정 시작 전까지 특이사항 잠금.
3. **투입 입력 방식 변경** — 투입 M/M과 **투입 비율(%)** 을 입력하면 투입 종료일을 자동 계산(M/M ÷ 비율, 시작일 기준)하고 날짜는 직접 수정 가능(수정 시 자동 모드 해제, 「자동 계산」으로 복귀). 중간에 투입이 비는 **공백 구간**을 여러 건 등록하면 그 기간은 월별 계획 투입률에서 제외. 비율이 없는 기존 데이터는 종전 방식(M/M ÷ 기간)으로 계산. **월별 조정(2026-10-22)**: 인력 행의 「월별 ▼」로 월 격자를 펼치면 자동 계산된 월 투입률(%)이 채워져 있고, 달라지는 달만 직접 고치거나 구간(예: 12~2월 60%)을 일괄 적용한다. 직접 고친 달만 「수정됨」으로 저장하고, 계획 합계와 입력 M/M의 차이를 표시하며, 자동 계산으로 되돌릴 수 있다. 월 투입률 105% 초과 달은 빨간 테두리. 변경 요청 비교에 투입 비율·공백 변경이 포함된다.
4. **프로젝트 접근 권한** — 투입 인력별 접근 권한(편집/열람, 관리자는 항상 관리)과 프로젝트 단위 「멤버 외 열람 제한」 설정. 변경은 기존 투입 계획 변경 요청·승인·이력 흐름을 따른다(관리자 변경 이력 포함). ※ 실제 열람 제한 적용은 백엔드 권한 구현 시.
5. **프로젝트 관리 항목** — 발주금액 **부가세 포함 여부** 추가, 통화는 원화 고정(제외), 실패/보류 사유를 **공통코드(사유 코드)** 선택 + 상세 텍스트로 분리(코드 필수).
6. **원가 구조 확장(간접비·가산율·난이도 가중·등급 이력)은 제외** — 필요 시 향후 적용.
7. **RFP 확정 M/D** — RFP 평가 관리에서 항목마다 **확정 평가자**를 고르면 그 평가자의 M/D가 확정 값이 되고 직접 수정 가능(「수정됨」 표시). 평가자 1명이면 제출 값이 기본 확정 값, 평가자 2명 이상이면 일괄 지정 보조 제공. 분류별·총합 소계 열 추가. 평가자별 값은 여전히 자동 취합하지 않는다.
8. **단계전환 승인·롤백** — 단계전환 실행은 「전환 요청(승인 대기)」을 만들고, 센터장·admin이 승인해야 WBS·문서 테일러링이 생성되고 「수행 중」이 된다(반려 사유 필수, 요청 취소 가능). 전환 후에도 진척 입력·이슈가 없으면 사유를 남기고 **롤백**(WBS·문서 삭제, 「수주」 복귀)할 수 있고 롤백 이력을 남긴다.
9. **고객사 열람자 역할은 두지 않는다(확정)** — 고객사 담당자에게 PMS를 노출하지 않는다. 고객 보고는 제출 완료된 보고서의 복사/엑셀/PDF 내보내기로 전달한다. 고객사 담당자는 마스터 데이터(고객사 관리)로만 관리하고 로그인 계정과 연결하지 않는다.
### 3.27 프로세스 현황 모달 (v2.8, 목업)

상태가 흘러가는 업무마다 「🔄 처리 현황」 버튼을 두고, 공통 모달로 **진행 단계(완료/현재/예정)**, **지난 처리 내역(일자·담당자·처리·내용)**, **현재 누구에게 있는지(현재 담당 + 해야 할 일)** 를 보여준다.
- 적용 화면: 단계전환 승인 요청, 투입 계획 변경 요청(이력·승인 대기 배너), 주간/월간 보고서(작성→제출→수정→재제출), 이슈(오픈→진행 중→해결→종결: 오픈·진행 중은 담당자, 해결은 보고자의 종결 확인), 제안서(작성 중→내부 검토→제출 완료→결과 확정, 버전 등록 이력).
- 현재 담당 규칙: 승인 요청은 승인자(단계전환=센터장·admin, 투입 변경=인력 관리자), 보고서는 프로젝트 관리자, 제안서는 작성 책임자(내부 검토는 검토자 미지정, 제출 완료는 발주사 결과 대기).
- 후속: 프로젝트(영업) 상태 흐름, RFP 평가 제출, 운영 이슈·운영 영업·차기 사업 기회·영업 인수인계에도 적용(현재는 상태 변경 이력을 저장하지 않는 화면이 많아 이력 저장부터 필요). ERD: 상태 변경 이력을 공통 이력 테이블(대상 유형·대상 ID·상태·처리자·일시·메모)로 둘지 검토.

### 4.5 사용자/계정 확장 (3.5, 3.7 반영 — 설계 시 중점 검토 필요)

- 협력사 인력까지 전원 계정을 준다는 것은, 기존 `module-user`의 `User`(테넌트 소속 자사 직원 개념에 가까움)를 그대로 쓸지, 아니면 **소속구분(자사/협력사)과 소속회사명 필드를 가진 확장 프로필**을 PMS 쪽에 별도로 둘지 결정이 필요함. 기존 프레임워크의 `Role↔UserGroup↔User` 권한 구조와 어떻게 맞물릴지도 함께 봐야 함(예: 협력사 인력은 "이 프로젝트의 담당자" 권한만 갖고 다른 관리 화면엔 접근 못 하게 하는 등).
- 로그인 후 개인화 To-Do 대시보드(3.7)는 이 계정 모델이 정해진 뒤 설계.

### 4.6 메신저 연동 — 텔레그램 + Mattermost (3.3, 3.8, 3.9.5 반영 — v1 포함)

- 알림 채널 추상화(발송/콜백 수신/사용자 매핑) + 채널별 구현체 2종, 프로젝트 단위 채널 선택
- Mattermost: 봇 계정 + REST API 발송, Interactive Message 버튼 콜백, 슬래시 커맨드, 다이얼로그. 사내 설치형이라 사용자 매핑은 loginId/이메일로 가능, 단 Mattermost → PMS 서버 콜백 경로(네트워크, 허용 내부 접속 설정)와 콜백 검증(토큰/서명) 필요
- 사용자 ↔ 텔레그램 chatId 연결 방법(봇에게 `/start` + 인증코드 방식이 일반적)
- 업무 도래 트리거(마감 D-day, 시작일 등) → 알림 발송 스케줄링 방식
- 알림 내 실적 입력 UX(인라인 버튼으로 퍼센트 단계 선택 vs 텍스트 응답 파싱)

## 6. 다음 단계 제안

**진행 순서(v0.4 조정): 요구사항 정의 → 화면설계(목업) → ERD 설계.** 화면설계로 고객과의 gap을 먼저 줄이고, 확정된 화면에서 필요한 데이터를 도출해 ERD를 만든다(화면설계 품질이 곧 프로젝트 리스크를 줄인다는 경험칙).
1. **화면설계(목업)**: 로그인 첫 화면 To-Do 대시보드, 프로젝트/멤버, WBS(트리 + 진척 입력 + 복사), 요구사항 → 태스크 생성, 이슈/리스크/산출물/비용, 간트·캘린더(목업), 초대/가입 승인, 메신저 설정 및 알림 메시지 — 정적 목업(프론트엔드 `pages/apps/PMS/`에 라우트만 등록, 더미 데이터)으로 고객과 검토
2. 화면에서 도출한 데이터 항목으로 `module-pms` 도메인 모델(ERD) 설계 — 4절 스케치를 구체화
3. 메신저 연동(텔레그램 + Mattermost)은 v1 포함으로 확정 — 알림 채널 추상화 설계와 PoC(발송 + 버튼 콜백)를 먼저 진행
4. 위 설계가 어느 정도 잡히면 `module-pms` 스캐폴딩 시작
